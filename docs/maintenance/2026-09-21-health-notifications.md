## 问题与边界

原 `deploy/bot/healthcheck.py` 在 `_notify()` 后无条件把当前 `problems` 写为去重状态，忽略
发送结果。`pdg-bot.py:post()` 返回原始 Telegram JSON，传输失败返回 `{}`；它不保证 API 接受
消息，`send()` / `send_plain()` 也不返回确认结果。因此全失败或部分失败都会被误当作已经
通知，同一故障此后不再重试。

此次继续复用 `checks.ALERT`、`checks.bot_credentials()`、`bot.post()` 与现有 10 分钟 timer，
只修改通知与状态持久化。没有引入队列服务、外部依赖、配置项或新的运维框架。

## 行为与状态协议

`/opt/pdg-bot/health-state.json` 的 `schema: 2` 为每个当前允许的收件人保存：

- `observed`：最近一次检查观察到的故障列表。
- `delivered`：最近一次收到 `bot.post()` 返回 JSON 中 `ok: true` 的状态；旧非空文件迁移时为
  `null`，表示此前是否送达未知。
- `pending`：待发消息种类、关联故障、失败计数和下一次允许尝试时间；确认成功后才清除。

顶层 `problems` 保留给旧版本读取，但仅在所有当前收件人都没有待发消息且确认状态一致时
更新。它不是新版本的去重依据。

| 情况 | 新行为 |
|---|---|
| 初次正常、持续正常，或已确认的故障未变化 | 不发消息 |
| 新故障、故障内容变化 | 先持久化待发记录，再逐收件人发送当前状态 |
| 网络异常、空/畸形响应、Telegram `ok: false` | 不推进 `delivered`；失败计数最多记到 4 |
| 部分收件人成功 | 每人独立保存结果；以后只重试未确认者 |
| 连续失败 | 间隔为 10、20、40、60 分钟，随后保持最多每 60 分钟一次；保留待发记录持续重试 |
| timer 重启或进程重启 | 从落盘的待发记录和时间继续；系统时钟后退时把等待上限收敛到 60 分钟 |
| 故障已经确认，随后恢复 | 发普通恢复消息；恢复发送失败也保留待发记录 |
| 故障尚未确认送达就恢复 | 用“期间异常已恢复，之前提醒未确认送达”合并说明，包含最近的故障，不先发过时故障 |
| 恢复尚未确认，原已确认故障再次出现 | 当前状态与最后确认状态一致，取消过时恢复；不重复故障 |
| 收件人增加/移除 | 新收件人接收当前故障；移除的收件人从下一轮状态中移除且不再发送 |

故障变化或恢复会替换过时待发消息并立即获得一次尝试，不等待旧事件的退避。此处是最新状态
合并，不是保存每次短暂故障的事件日志。每轮每个到期收件人至多调用一次 `bot.post()`；该
既有函数在连接失败时内部会再尝试一次连接。当前失败会以非零退出码和脱敏的通用日志说明；
等待下次重试期间正常返回，待发记录继续保留。消息改为纯文本并限长，避免检查详情中的 HTML
字符或过长内容让整条消息永久被拒绝。

旧 `{"problems": []}` 作为正常基线，不制造恢复消息；旧非空状态没有可靠送达证据，因此在
仍有故障时保守重报一次，若已经恢复则发一次合并恢复说明。只有明确确认成功才结束重试。

这采用至少一次重试语义，不承诺最终一定送达或绝不重复。服务端已接收，但响应丢失，或接收
之后、写盘确认之前崩溃时，下一轮可能重复；`bot.post()` 的连接重试也有同样的不确定窗口。
没有另一个可信回执服务时不能消除这种歧义。

## 文件安全、并发与恢复

- 使用同目录 `health-state.json.lock` 的非阻塞 `flock`；并发调用中拿不到锁的一方失败退出，
  不发消息、不覆盖状态。锁只覆盖此健康通知流程，不改变配置事务锁。
- 每次先保存新观察和待发状态，再发送；每个收件人的结果立即单独保存，减少后续失败导致
  已成功收件人重复收到的范围。
- 在同目录创建 0600 临时文件、flush/fsync、原子 replace，并在 Linux fsync 父目录；更新前
  与打开后检查常规文件、链接数和权限。允许现有 root-owned 0644 状态与 0755 脚本目录，
  新写状态收紧为 0600，不 chmod 或迁移脚本目录。
- 拒绝状态/锁符号链接、硬链接、非普通文件、组/其他用户可写的状态或父目录、异常 owner、
  非法/不一致 schema 和超过 1 MiB 的文件；保留现场且不发送。日志不打印路径内容、API
  响应或异常正文。损坏状态的修复需要在授权维护中保留受保护副本，再恢复已验证的状态，
  不自动清空或将未知状态当成成功。

本地回退可以撤销本次提交；由于未部署，没有生产状态需要回退。未来若要降回只认识旧
`problems` 的实现，应先获得部署/维护授权，暂停健康通知 writer 并安全保存当前状态。
只有所有收件人 `pending` 均为空、`delivered` 相同、且顶层 `problems` 等于该值时，旧实现
才有一致的去重视图。存在待发或送达分歧时不要无条件降级或删除状态；优先修复当前实现，
或由管理员明确记录与处理未确认通知后再决定旧版恢复。即使降级条件满足，旧实现发送失败
仍会重现原缺陷。本轮没有执行这些操作。
